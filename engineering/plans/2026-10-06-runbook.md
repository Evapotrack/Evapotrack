## 2. Best overall plan

**One rule:** `main` always equals what is live, both the App Store app and evapotrack.com. Everything unreleased waits on a release branch.

```
main ──●── (B) tags v1.0, v1.1 · version 1.1 · this branch merged
       │
       ●── (C) website corrections (photo-free) ── live immediately
       │
       └──► release/1.2 ── (D) merge revision 2 ── (E) build/test fixes ── (F) archive 1.2
                                                                          │
main ◄────────────────── release day: merge release/1.2, tag v1.2 ◄──────┘
```

**Why this shape:**
- **The website deploys from `main`.** Holding the photo text on a branch is the only way to avoid advertising a feature that isn't out yet. Then the app and site change on the same day.
- **Tags make the history permanent.** Any past version can be rebuilt (`git checkout v1.1`) without keeping a second copy of the app.
- **Revision 2 is the best base for 1.2.** It is verified against the shipped schema (V5) and merges cleanly (V6). It carries every fix from the September audit and the permission-free photo design. The camera branch conflicts with it (V7) and would add a camera-permission prompt and an unversioned schema change.
- **Each phase can stop safely.** If 1.2 takes months, `main` stays correct, the website is already fixed, and history is recorded.

Order: **A** (facts) → **B** (record history) → **C** (website) → **D** (release branch) → **E** (build and test on the Mac) → **F** (release). A–C need about an hour of your time. E is the long part.

## Phase A: Secure the facts (Mac, ~30 min, before anything else)

### A1. Confirm the release in App Store Connect
- **Why:** You didn't expect this update. Confirm that v1.1 was released by you, when, and that the account is healthy, because the July notes said the account was locked.
- **How:** appstoreconnect.apple.com:
  1. Apps › Evapotrack › **App Store** tab › the version list on the left: note when 1.1 became "Ready for Distribution".
  2. **TestFlight** tab › Builds › iOS: note the upload date of 1.0 (1) and 1.1 (1).
  3. **Users and Access**: only people you recognize; under Integrations › App Store Connect API, only keys you created.
  4. **Business** (Agreements, Tax, and Banking): no agreement waiting for acceptance.
  5. developer.apple.com › Account › Membership: Active, renewal date, auto-renew on.
  6. Your Apple Account › Sign-In & Security: the trusted phone number is your current one; remove the expired one.
- **Check:** write the two dates in `engineering/releases/README.md` (or send them and a cloud session will).
- **If something looks wrong:** unknown user or key → remove it and change your Apple Account password. Pending agreement → accept it, or the next submission is silently blocked.

### A2. Snapshot your Mac's working copy before pulling anything
- **Why:** v1.1 was archived with version 1.1, and that number was never committed (V3). Your Mac may hold uncommitted or unpushed changes, possibly the only exact copy of what shipped. A careless `git pull` or reset could lose them.
- **How** (Terminal, in your Evapotrack folder):
  ```sh
  git status                    # uncommitted changes?
  git stash list                # stashed work?
  git fetch origin
  git log --oneline origin/main..HEAD   # local commits not on GitHub?
  git diff                      # look at what changed
  ```
  If anything shows up, save it on its own branch. Add files by name after reading the list; never add certificates (`.p12`, `.cer`), provisioning profiles, `.env` files or anything from `private/`:
  ```sh
  git switch -c mac-snapshot-2026-10-06
  git add EvapotrackDev.xcodeproj/project.pbxproj   # plus any other files you recognize
  git commit -m "Snapshot of the Mac working copy as of 2026-10-06 (v1.1 archive state)"
  git push -u origin mac-snapshot-2026-10-06
  git switch main
  ```
- **Check:** `git status` is clean on `main`, and the snapshot branch is on GitHub.
- **If it goes wrong:** nothing is lost while the files are on disk. Stop and ask before running `git reset`, `git checkout -- .` or `git clean`.

### A3. Read the archive times in Xcode Organizer
- **Why:** they decide which commit becomes the `v1.0` tag (`23611ba` or `fed761b`, both 2026-03-25) and confirm `v1.1` = `c063360`.
- **How:** Xcode › Window › Organizer › Archives › Evapotrack. Each archive shows date, time and version (build). Note the time of the uploaded 1.0 (1) and 1.1 (1).
- **Check:** the commit for each tag is the last one before its archive time. Commit times are US Eastern (−0400):
  ```sh
  git log --until="2026-03-25 18:00 -0400" -1 --format='%h %ad %s' main -- Evapotrack EvapotrackDev.xcodeproj
  ```
- **If the archives were deleted:** use the TestFlight upload dates from A1 instead. If it's still ambiguous, tag `v1.0` on `fed761b`, the later candidate. The two differ only in in-app help text, and the tag message says so.

### A4. Back up before any testing
- **Why:** later steps install test builds over the App Store app. A database upgraded by 1.2 can't be opened by 1.1 again, because SwiftData doesn't migrate backwards.
- **How:** Mac: Time Machine or a copy of the project folder. iPhone: Finder › your iPhone › "Back Up Now" (or an iCloud backup). In Evapotrack: export any grow you care about (open the grow › gear icon › Download Data). Your screenshots show only the Example Grow, so the risk on this phone is low.

## Phase B: Record the history (Cloud with your OK, or Mac; ~15 min)

### B1. Create release tags `v1.0` and `v1.1`
- **Why:** this is the clean, safe way to keep each released version in the repo (see the review, §6). A tag is a permanent, named pointer to the exact source. It duplicates nothing and confuses neither Xcode nor search, and `git checkout v1.1` or `git archive v1.1` gives back exactly what shipped.
- **How** (after A3):
  ```sh
  git tag -a v1.0 <commit from A3> -m "Evapotrack 1.0 (1), first App Store release (archived <date/time>)"
  git tag -a v1.1 c063360 -m "Evapotrack 1.1 (1); MARKETING_VERSION was set to 1.1 in Xcode at archive time and committed later"
  git push origin v1.0 v1.1
  ```
  Optional: on GitHub › Releases › "Draft a new release", pick each tag and paste its entry from `engineering/releases/README.md`. That gives a downloadable page per version.
- **Check:** `git show v1.1 --stat` shows the right commit; the tags appear on GitHub.
- **If it goes wrong:** a mistaken tag can be removed before anyone relies on it: `git tag -d v1.0 && git push origin :refs/tags/v1.0`. Never move a tag after a release is built from it.

### B2. Commit version 1.1 to `main`
- **Why:** the repo must match what is live (V3). Otherwise the next archive comes out as 1.0, which App Store Connect rejects, and the history keeps saying the wrong thing.
- **How:** in Xcode, select the project › each target (EvapotrackDev and EvapotrackDevTests) › General › Identity › Version = **1.1**; leave Build at **1**. Or, the identical edit, which is what the cloud would do:
  ```sh
  sed -i '' 's/MARKETING_VERSION = 1.0;/MARKETING_VERSION = 1.1;/' EvapotrackDev.xcodeproj/project.pbxproj   # Mac (BSD sed)
  ```
  Commit message: `Record the shipped version: 1.1 (1)`.
- **Check:** `grep -c "MARKETING_VERSION = 1.1" EvapotrackDev.xcodeproj/project.pbxproj` prints **4**; the app builds (⌘B).
- **If it goes wrong:** `git revert` the commit; it touches one file. Trial-merged with revision 2 with no conflict (V8).

### B3. Merge this branch (`claude/vibrant-noether-xzeec1`) into `main` through a pull request
- **Why:** it holds the release record, these plans, the v1.1 device screenshots and the sticker. None of it is under `docs/`, so nothing on the website changes (V14). A PR, the repo's first (V16), leaves a reviewable record.
- **How:** a cloud session can open the PR when you ask (B2's version commit can ride in it). Then on GitHub, review and "Create a merge commit".
- **Check:** `main` now has `engineering/releases/`, `engineering/plans/` and `marketing/sticker/`; evapotrack.com looks the same.

## Phase E: Build and test on the Mac (Mac + Cloud; the long phase)

1. You build.
2. You copy the errors (Issue navigator › select all › Copy) into a cloud session.

4. You `git pull` and build again.

  2. Open `EvapotrackDev.xcodeproj` in Xcode 26.2+ (V17).

### E2. Run the tests
- **How:** Product › Test (⌘U).

### E3. Capture a real v1.1 database for the migration test
- **Why:** it proves the upgrade keeps everything, using a database written by the code that is actually live.
- **How:**

## Phase F: Release 1.2 (Mac)

### F1. Archive from a committed state
- **Why:** this is the root cause of today's confusion (V3/V13). The commit you archive must contain exactly what ships.
- **How:**
  1. `git status` is clean on `release/1.2`, and the version is 1.2 (1).
  2. Product › Archive with "Any iOS Device (arm64)" selected.
  3. In Organizer: **Validate App**, then **Distribute App › App Store Connect › Upload**.
  4. Note the commit: `git rev-parse --short HEAD`.
- **If App Store Connect rejects the build number** (for example after a re-upload): bump the build to 2, commit, and archive again. Never reuse a version + build pair.

### F2. TestFlight on your own iPhone
- **Why:** installing the TestFlight build over the App Store v1.1 is the real-world upgrade on real hardware, before any user gets it.
- **How:**
  1. In App Store Connect › TestFlight, add the build to **Internal Testing** (internal testers need no Beta Review).
  2. Install it on the iPhone through the TestFlight app. It replaces the App Store app and keeps the data.
- **Check:** your Example Grow and its logs are intact, and Settings shows **v1.2 (1)**. Repeat the photo and text-size checks on the device.

### F3. Submit for review
- **How:** App Store Connect › Evapotrack › "+" version **1.2**:
  - **Build:** select the one from F1.
  - **What's New:** EN (and ES if the listing has a Spanish localization). Mention optional photos, the smarter Next recommendation, decimal-comma input and Edit Plant.
  - **App Privacy:** stays "Data Not Collected". Photos never leave the device, and no new permission is used, so no new key is needed.
  - **Review notes:** "Photos are optional, chosen with the system photo picker, and stored only on the device. No account or network use."
  - **Version Release:** choose **"Manually release this version"**, so you control the moment the app and website change together. Turn on **Phased Release for Automatic Updates** (over 7 days; you can pause if a problem appears).
- **If rejected:** answer in the Resolution Center; fix on `release/1.2`; upload build 2.

### F4. Release day (same hour)
1. App Store Connect › **Release This Version**.
2. Merge `release/1.2` into `main` by PR. GitHub Pages publishes the photo text, privacy policy and support FAQ within minutes.
3. Tag the archived commit and push:
   ```sh
   git tag -a v1.2 <commit from F1> -m "Evapotrack 1.2 (1)"
   git push origin v1.2
   ```
4. Add the 1.2 entry and screenshots to `engineering/releases/`.
5. Later, re-shoot the website carousel screenshots on 1.2. That is a website-only change, safe on `main` any time after release.

### F5. The first two weeks
- **Watch:** Xcode › Organizer › Crashes, and App Store Connect › Ratings and Reviews.
- **If a serious bug appears:** pause the phased release. Then branch `hotfix/1.2.1` from the `v1.2` tag, fix, release 1.2.1, and merge the fix back to `main`. An App Store version can't be rolled back, only replaced.
- **Data safety:** revision 2 never replaces a database it can't open. It shows an error screen instead, so a migration bug is fixable by update without data loss.
